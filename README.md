## ◈ The Philosophy

Writing code is easy to celebrate. Building software that people can actually trust, understand, and use is the real challenge.

**Full-Stack Vibe Coding Skill** is a reusable set of engineering instructions for AI coding assistants and developers who want to move beyond quick prototypes and produce polished, maintainable applications.

It combines full-stack engineering, thoughtful interface design, security-conscious development, systematic testing, and project continuity into one practical standard.

The goal is simple:

> Build software that works as beautifully as it looks, protects its users, and remains understandable as it grows.

## ⌘ Getting Started

### 1. Clone the repository

Replace `YOUR_USERNAME` and `YOUR_REPOSITORY` with your actual GitHub username and repository name.

```bash
git clone https://github.com/YOUR_USERNAME/YOUR_REPOSITORY.git
cd YOUR_REPOSITORY
```

### 2. Add the skill to your project

Place `skill.md` inside your website's root directory.

```text
my-website/
├── skill.md
├── PROJECT_CONTEXT.md
├── README.md
├── .env.example
├── .gitignore
├── src/
├── tests/
└── docs/
```

Adjust the folder structure to match your actual framework and project.

### 3. Give your AI coding assistant the instructions

Ask your coding assistant to read `skill.md` before making changes.

Example prompt:

> Read `skill.md` completely and follow its engineering standards throughout this project. Inspect the existing codebase before modifying anything. Preserve working features, prioritize security and excellent UI/UX, implement complete functionality, test changes where possible, and update `PROJECT_CONTEXT.md` after significant milestones. Never claim that something works or is secure unless the available evidence supports that claim.

### 4. Keep the project context updated

Use `PROJECT_CONTEXT.md` to record the architecture, completed features, database schema, design decisions, known issues, and next development tasks.

This helps you continue working across different sessions without unnecessarily rebuilding the application or losing important decisions.

Every meaningful feature should follow a repeatable cycle:

1. Understand the requirements and acceptance criteria.
2. Inspect the existing implementation and identify risks.
3. Design the simplest architecture that meets the requirements.
4. Implement the feature with real behavior and appropriate error handling.
5. Verify security, permissions, responsiveness, and functionality.
6. Check for regressions and document outstanding issues.
7. Update the project context before moving forward.

## ⛨ Quality Standard

The objective is not to make unsupported claims about perfection. It is to establish a disciplined standard for continuous improvement.

| Area | Expected standard |
|:--|:--|
| Functionality | Features work end to end, not just visually |
| Security | Appropriate protections and server-side access checks |
| UX | Clear navigation and predictable interactions |
| Responsive design | Usable across phones, tablets, and desktops |
| Accessibility | Semantic structure, keyboard support, and readable contrast |
| Performance | Efficient rendering, queries, and network requests |
| Maintainability | Understandable code and documented architecture |
| Testing | Verified behavior with honest reporting of results |
| Continuity | Current project documentation and preserved functionality |

**Security note:** No instruction file can guarantee zero vulnerabilities. Production applications still require ongoing updates, monitoring, appropriate security testing, and additional review based on the sensitivity of their data.

## ▣ Repository Structure

```text
.
├── README.md
├── skill.md
├── PROJECT_CONTEXT.md
├── .env.example
├── .gitignore
├── src/
├── tests/
└── docs/
```

- `README.md` — project overview and usage instructions.
- `skill.md` — reusable full-stack development standards.
- `PROJECT_CONTEXT.md` — project-specific architecture and progress.
- `.env.example` — documented environment variable names with placeholder values only.
- `src/` — application source code.
- `tests/` — automated tests.
- `docs/` — architecture, setup, and technical documentation.

This is a suggested structure, not a requirement to create empty folders in every project.

## ◇ Core Principles

```text
QUALITY OVER SHORTCUTS
SECURITY OVER CONVENIENCE
USABILITY OVER DECORATION
CLARITY OVER COMPLEXITY
TESTING OVER ASSUMPTIONS
PRESERVATION OVER RECKLESS REWRITES
```

The best implementation is not necessarily the one with the most code or the newest technology. It is the one that meets the requirements reliably, minimizes unnecessary complexity, and respects the people who will use and maintain it.
